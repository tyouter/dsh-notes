# 召唤师：从"一次 LLM 调用"到"带工具与记忆的 agent"

> 2026-11-11。起因：试用中反复出现"召唤师不智能"——指定黄仁宇却让徐霞客答、自己抢答内容、
> 刚请来的人不说话、把口述错字当成对方的话。本文分析原因、比较几种架构、给出分阶段方案。
> 结论先行：**不是 prompt 不够长，是现在的召唤师没有记忆、没有工具、没有自检**。

## 1. 现状

每次停顿一次调用：

```
system（规则 + 名单 + JSON 格式） + user（在座 / 上一份差事 / 上一轮台词 / 三段上下文）
   → 一次生成 → normalizePlan 机械校验 → 客户端执行
```

优点：便宜、快、可预测。缺点：**它是一次性判断**——看到什么就答什么，没有"想一想再答"的余地。

## 2. 失败案例归因

| 现象 | 表层原因 | 结构原因 |
| --- | --- | --- |
| 指定黄仁宇，徐霞客答 | 模型没把"该他答"落到 speak | 没有"用户点名的实体 → 必须在 speak 里"的硬校验 |
| 召唤师自己答内容 | host 模式被滥用 | 没有区分"调度问题"和"内容问题"的后置检查 |
| "到了，徐霞客在"但不说话 | 只写了 say 没写 speak | 没有 **say 里出现的承诺必须可执行** 的校验 |
| 刚请来的人被换掉 | 房间靠模型每轮重写 | 状态不在客户端/文件里，而在模型的短期注意力里 |
| 把人名听错当成别人 | 模型按字面理解 | 没有"实体消歧"这一步（名单 + 上下文） |
| 反复道歉/复读 | 看到自己上一句就顺着说 | 没有跨轮记忆，只有一份"上一份差事" |

共同点：**都是"判断"错，不是"格式"错**。加提示词能缓解，但不会根治——因为提示词是"同一口气里说完"。

## 3. 候选架构

### A. 纯 LLM（现状）
- 智能上限：受单次上下文与采样随机性限制
- 延迟：1 次调用（~1–3s）
- 成本：低（~1.5k in / 200 out）
- 可调试性：只有最终 JSON，错了不知道为什么
- 失败模式：选错人、抢答、承诺不执行

### B. LLM + 结构化状态 + 校验/重试（增强版现状）
- 把"房间、差事、最近台词"从模型注意力挪到客户端状态（已有部分）
- normalize 之后加**语义校验**：承诺/指定/在座一致性；不通过则带着错误原因重试一次
- 智能上限：略高于 A；能挡住"低级错误"，挡不住"判断偏差"
- 延迟：1–2 次调用；成本：+30%
- 可调试性：好（每次失败都有原因）
- 这是**性价比最高的一步**

### C. 工具型 agent（推荐下一阶段）
- 召唤师拥有少量工具，自己决定用不用：
  - `room()` 看当前在座与最近谁说过话
  - `turns(n)` 读最近 n 轮（谁说了什么）
  - `find_person(query)` 在名单/别名里找人（解决"修摩罗什""易道"这类）
  - `create_person(spec)` / `dismiss(id)`
  - `set_plan(plan)` 提交计划（带自检）
- 智能上限：明显高于 B——它可以"先查再答"
- 延迟：2–4 次小调用（每次输出很短）
- 成本：2–3 倍
- 失败模式：工具调用发散；需要步数上限与超时

### D. Super-agent（主持人 + 评审 + 客人）
- 主持人 agent 负责调度；**评审 agent** 只在"计划不一致 / 用户抱怨 / 低置信"时介入，判定要不要重做
- 客人各自是独立的小 agent（有自己的记忆、可以多轮）
- 智能上限：最高；也最像"会客厅"
- 延迟/成本：3–6 倍；调试复杂
- 适合做，但**不适合现在做**——先把 C 跑稳

## 4. 推荐路线

### P0（这周，改动最小）
1. **状态外置**：`salon.jsonl` 记录每轮 plan + 实际执行结果（谁说了什么），客户端/宿主都能读。
2. **语义校验 + 重试**（在 `normalizePlan` 之后）：
   - 用户点名了 A，speak 里没有 A → 不通过
   - say 里有"请/叫/让 X""到了/在" 但既没有 create 也没有 speak → 不通过
   - speak 里的人不在 room → 自动并回 room
   - 同一句台词 10 分钟内重复 → 不通过
   - 不通过就带错误原因重试一次（同一 system，user 追加"上一次的问题"）
3. **host 模式的硬边界**：host 且 speak 为空时，只允许"调度类"台词（长度/句式可判），否则降级为 reply。

### P1（下一步）
4. 工具型召唤师：`room / turns / find_person / create / dismiss / set_plan`，最多 3 步。
5. `find_person` 内置别名与模糊匹配（语音常错的人名），返回候选而不是猜。
6. 计划里带 `confidence` 与 `reason`，低置信时走"再问一次"或保持安静。

### P2（看效果）
7. 评审 agent：只在 P0 校验失败或用户说"不智能/不对"时触发，输出"错在哪 + 新计划"。
8. discuss 变成真多轮：每轮把上一句交给下一位，最多两轮。
9. 把 2 秒闸门、maxGuests、重试次数暴露到 `settings.json`。

## 5. 成本与延迟预算（粗略）

| 架构 | 每停顿调用 | 输入 tokens | 延迟 | 备注 |
| --- | --- | --- | --- | --- |
| A 现状 | 1 | ~1.5k | 1–3s | 便宜但常错 |
| B 校验+重试 | 1–2 | ~1.8k | 1–5s | 只在失败时重试 |
| C 工具 agent | 2–4 | ~3k | 3–8s | 需要步数上限 |
| D 主持+评审 | 3–6 | ~5k | 5–15s | 只在争议时启用评审 |

判断：**B 先行**，因为它能在不显著增加延迟的情况下挡住今天遇到的大部分"不智能"。

## 6. 需要记录的指标

没有指标就无法判断"变聪明了没有"。建议在 `events.jsonl` 里记：

- `plan.mode / speak[].id / timing`
- 是否命中校验失败、失败原因、第几次重试成功
- 用户下一句是否点名同一个人（"该他答"）= 选错人的信号
- 用户说"不智能/不对/你没听懂"= 负面信号

用这些离线算三个率：
1. **指定命中率**：点了 A，A 是否开口
2. **越权率**：召唤师是否答了本该客人答的内容
3. **沉默率**：该答时没人答（含 say 承诺但未执行）

## 7. 不做什么

- 不在这一版引入完整的"多 agent 会话编排"——延迟和调试成本都撑不住。
- 不把召唤师换成一个完整宿主 session（`notes_board` 那种）——每次停顿起一个 session 太重。
- 不继续加关键词规则（已经被证明是补丁）。
